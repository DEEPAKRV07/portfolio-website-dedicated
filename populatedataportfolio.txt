# 3. Cinematic Hero System

One of the largest frontend challenges was the hero.

The project experimented with a dedicated ambient video and eventually moved toward using the cinematic video as a **full hero background**.

# Production Safety

An important database issue was also encountered during development.

The Payload/Drizzle development configuration attempted to push schema changes automatically and detected potentially destructive changes in `homepage_blocks`.

The system presented warnings such as deletion of existing columns.

Instead of accepting the schema push, the configuration was changed to:

```text
push: false
```

This prevented accidental schema modification during development.

That was an important production-safety decision.

# SightMate — Comprehensive Project Summary

## 1. Project Overview

**SightMate** is an AI-powered mobile assistive application designed to help **blind and visually impaired users understand their surroundings, read environmental text, receive navigation guidance, and interact with a smartphone through voice and accessible input methods**.

The project combines **computer vision, on-device machine learning, speech technologies, OCR, semantic scene understanding, and accessibility-focused UI/interaction design** into a single Flutter-based Android application.

The central idea is:

> **Camera / Voice / Touch Input → AI & Scene Processing → Decision Logic → Audio Guidance**

Rather than depending on a single AI model, SightMate combines multiple perception and interaction components so that different capabilities can be used for different situations.

---

# 2. Problem Being Addressed

People with visual impairments may face difficulties with:

* Identifying objects around them
* Understanding whether an obstacle is directly ahead
* Determining a safer direction to move
* Reading printed text
* Accessing information such as time, date, battery level, and location
* Interacting with conventional smartphone interfaces
* Receiving information without relying on visual feedback

SightMate addresses these challenges by converting visual and system information into **spoken, actionable feedback**.

For example:

**Camera sees:**

> TV in the center of the scene

The system can provide:

> **“TV ahead.”**

If the navigation system determines that the center path is blocked while the left side has lower danger:

> **“Move left.”**

---

# 3. Main Objectives

The main objectives of SightMate are:

### Environmental awareness

Use the smartphone camera and computer vision models to identify objects in the user's surroundings.

### Navigation assistance

Analyze the scene spatially and provide simple directional guidance such as:

* **Path clear**
* **Move left**
* **Move right**
* **Object ahead**
* **Obstacle ahead**

### Text accessibility

Use OCR to recognize visible printed text and convert it into speech.

### Hands-free interaction

Allow users to control important application functions using voice commands.

### Accessible information access

Provide spoken information about:

* Battery
* Time
* Date
* Location

### Alternative text input

Provide a Braille-style touch keyboard for entering text without depending on conventional visual keyboard interaction.

### Multilingual assistance

Provide speech translation functionality using the translation module.

---

# 4. Core Features Implemented

## 4.1 Object Detection

SightMate uses a **YOLOv8 TensorFlow Lite model** for mobile object detection.

The camera captures the environment and the model identifies objects with:

* Object class
* Confidence
* Bounding-box position

The detected objects are displayed visually using bounding boxes and can also be announced through TTS.

For example:

> “I see person on your left.”

or

> “I see TV in front.”

The detection pipeline is implemented through a dedicated `YoloService`, keeping the ML inference separate from the UI.

---

# 5. Navigation Assistance

Navigation is one of the main components of the project.

Instead of treating object detection as the complete navigation solution, SightMate combines:

**Object Detection + Semantic Segmentation + Navigation Fusion**

The camera frame is analyzed from three approximate spatial regions:

```text
        CAMERA VIEW

     LEFT | CENTER | RIGHT

       ↓       ↓       ↓
     danger  danger  danger
```

The system evaluates the relative danger in these regions.

The object detector contributes information such as:

* What object is present
* Where it is located
* How large it appears in the frame
* Detection confidence

The segmentation system contributes scene-level information about the image.

These outputs are passed to the:

### `NavigationFusionService`

The fusion logic combines the values and determines an appropriate navigation response.

Examples include:

```text
Move left
Move right
Path clear
TV ahead
Person ahead
Obstacle ahead
```

This is more useful than simply announcing every detected object because the goal is to provide **short, actionable guidance**.

---

# 6. Semantic Segmentation

SightMate also includes a TensorFlow Lite semantic segmentation pipeline.

The current segmentation model accepts an input tensor of:

```text
[1, 257, 257, 3]
```

and produces:

```text
[1, 257, 257, 21]
```

The segmentation output is converted into a pixel-level class mask.

The scene is then analyzed spatially to estimate the presence of relevant classes in the:

```text
Left
Center
Right
```

regions.

A visual segmentation overlay can also be displayed over the camera feed.

This gives the application an additional layer of **scene understanding beyond bounding-box detection**.

---

# 7. Navigation Fusion Logic

The navigation system doesn't simply say:

> “Object detected.”

Instead, it calculates a danger value based on information such as:

* Position
* Bounding-box height
* Detection confidence
* Segmentation-derived region information

For detected objects, the current implementation uses a danger contribution based on:

```text
object height² × confidence
```

Larger objects in the camera view therefore contribute more strongly to the perceived danger.

The result is combined with segmentation values:

```text
YOLO information
       +
Segmentation information
       ↓
Navigation Fusion
       ↓
Left / Center / Right decision
       ↓
Voice instruction
```

This gives the system a basic spatial decision layer rather than relying solely on raw object detection.

---

# 8. Distance / Proximity Reasoning

SightMate does not currently use a dedicated depth sensor.

Instead, the navigation logic uses **visual proximity cues**, particularly the relative size of detected objects in the camera frame.

A larger bounding box generally indicates that an object is visually closer or occupies more of the user's field of view.

Therefore:

```text
Small bounding box
       ↓
Lower danger contribution

Large bounding box
       ↓
Higher danger contribution
```

This provides a lightweight approximation of obstacle proximity that can operate with a normal smartphone camera.

It should be described as **visual proximity estimation**, rather than claiming exact physical distance measurement.

---

# 9. OCR / Text Reading

SightMate integrates **Google ML Kit Text Recognition**.

The OCR pipeline:

```text
Camera/Image
     ↓
ML Kit Text Recognition
     ↓
Recognized text
     ↓
Text filtering
     ↓
TTS
     ↓
Spoken output
```

The OCR service includes:

* Processing protection
* Text cleaning
* Minimum text-length filtering
* Similarity checking
* Speech cooldown
* Processing throttling

The interaction design also supports controlled actions such as:

* **Tap → read**
* **Double tap → rescan/re-read**
* **Swipe down → stop/exit**

This is particularly useful because continuous OCR processing can repeatedly recognize the same text from a stationary camera view.

The filtering mechanism separates **automatic duplicate suppression** from **intentional user-triggered rescanning**, allowing the same document/sign/text to be read again when the user explicitly requests it.

**Input Football Video → YOLOv8 Detection → ByteTrack Tracking → Camera Motion Compensation → View Transformation → Ball Interpolation → Speed & Distance Calculation → Team Assignment → Ball Possession → Visualization → Output Video**

# 1. Football Object Detection

The first stage identifies important objects in each frame of the football match.

The project uses **YOLOv8** with a trained football-specific model to detect:

* Players
* Ball
* Goalkeeper
* Referee

The repository contains a trained `best.pt` model and documents training on a custom football dataset containing these four classes. ([GitHub][1])

The detector produces bounding boxes and confidence scores for detected objects. These detections become the foundation for all subsequent analytics.

Instead of simply detecting objects independently in every frame, the detections are passed into the tracking pipeline so that individual players can maintain identities over time.

---

# 2. Multi-Object Tracking with ByteTrack

Detection alone cannot tell the system whether a player detected in the current frame is the same player detected in the previous frame.

To solve this, the project uses **ByteTrack** for multi-object tracking.

ByteTrack associates detections across consecutive frames and assigns tracking IDs to objects. This allows the system to maintain player trajectories throughout the video.

For example:

**Frame 100 → Player ID 7**
**Frame 101 → Player ID 7**
**Frame 102 → Player ID 7**

This persistent identity information is essential for calculating:

* Distance travelled
* Player speed
* Movement trajectories
* Possession
* Individual player statistics

The repository integrates ByteTrack through the `supervision` package and maintains tracked data frame by frame. ([GitHub][1])

---

# 3. Camera Movement Estimation

One of the major challenges with football footage is that the camera itself is constantly moving.

If the camera pans or shifts, the apparent position of every player changes even though the players may not have moved by the same amount on the actual pitch.

The project therefore includes a dedicated **camera movement estimator**.

Optical-flow-based motion estimation is used to identify camera movement between frames. The estimated movement is then used to compensate player positions.

This makes movement calculations more meaningful because the system attempts to separate:

**Actual player movement**

from

**Movement caused by the camera.**

This is particularly important when calculating player speed and distance.

Your repository contains a dedicated `camera_movement_estimator` component and also caches camera-motion information through the `stubs` system. ([GitHub][1])

---

# 4. View Transformation

Raw image coordinates do not directly represent positions on a football pitch.

For example, a player moving 50 pixels near the camera may represent a very different real-world distance from a player moving 50 pixels farther away.

The project therefore includes a **view transformation** stage to transform tracked positions into a more useful field-level representation.

This provides a foundation for tactical visualization and more consistent movement analysis.

The repository explicitly lists view transformation as one of its core pipeline features. ([GitHub][1])

---

# 5. Ball Tracking and Missing Detection Handling

Tracking the football is one of the most difficult parts of the system.

Unlike players, the ball is:

* Very small relative to the frame
* Extremely fast
* Frequently occluded
* Easily hidden behind players
* Sometimes difficult to detect during rapid movement

A missed detection can create gaps in the ball trajectory.

To address this, the project implements **linear interpolation** for missing ball positions.

If the ball is detected before and after a short detection gap, the system estimates the intermediate positions rather than leaving the trajectory discontinuous.

For example:

**Detected → Detected → Missing → Missing → Detected**

can be converted into an estimated continuous trajectory:

**Detected → Estimated → Estimated → Estimated → Detected**

This improves the continuity of ball movement and helps downstream possession and trajectory analysis.

The repository explicitly includes ball-position interpolation as part of the full pipeline. ([GitHub][1])

---

# 6. Team Classification

Another important component is determining which team each player belongs to.

Rather than manually assigning every tracked player, the system analyses the **jersey colors** of detected players.

Color-based clustering, including **KMeans clustering**, is used to identify dominant jersey-color patterns and separate players into teams.

This allows the system to associate tracked players with:

**Team 1**

and

**Team 2**

while keeping referees separate.

This becomes important for calculating team-level possession and displaying team-specific visualizations.

The repository identifies team classification based on jersey colors as one of its core features. ([GitHub][1])

---

# 7. Player Speed Estimation

Once player identities and positions are available across frames, the system can estimate player movement.

The system compares player positions between frames and uses the video frame rate together with transformed spatial coordinates to estimate movement speed.

This enables the generated analysis to associate movement metrics with individual tracking IDs.

For example:

**Player ID → Distance travelled → Average/instantaneous movement speed**

The project contains a dedicated `speed_and_distance_estimator` module for this functionality. ([GitHub][1])

---

# 8. Distance Covered

The system also estimates the distance travelled by individual players during the analyzed portion of the match.

Instead of simply looking at the player's bounding-box movement in raw image pixels, the project uses the transformed positions and camera-motion compensation to make the calculation more representative of actual movement.

This enables statistics such as:

**Player 7 → Total distance travelled**

and can potentially be extended into more advanced physical-performance analytics.

---

# 9. Ball Possession Analysis

The system also determines which player is currently closest to or associated with the ball.

The player-ball assignment component uses the spatial relationship between detected players and the ball to determine the player controlling the ball.

Possession can then be aggregated at the team level.

For example:

**Team A → 56% possession**
**Team B → 44% possession**

The repository includes a dedicated `player_ball_assigner` component and displays ball-control information in the final output. ([GitHub][1])

The output can contain:

The scheduler is integrated into the SQLite queue/resume architecture rather than being just a superficial loop.

# 🔁 4. Item-Level Resume System

The scraper doesn't simply remember:

> "I finished Chennai."

It tracks progress down to the individual business item:

```text
Category
   ↓
Location
   ↓
Business Index
   ↓
Google Maps URL
   ↓
Processing State
```

Therefore, if the program stops unexpectedly, it can continue from the appropriate point rather than starting the entire search again.

The README specifically documents the system as:

> `Category → Location → Business Index → Item State`

and confirms that a timed run or manual interruption can resume from the next item. ([GitHub][1])

# 🛡️ 13. Reliability & Recovery

A significant part of the project evolved around making long-running scraping safer.


Long-running browser sessions can periodically recycle their context to reduce memory accumulation.

### Logging

Logs are separated into:

```text

├── database/
└── errors/
```

The repository structure documents these reliability components. ([GitHub][1])
